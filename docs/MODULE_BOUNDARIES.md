- مخزن مجاز: `miadjaberi/asrar-azal-test`

- این سند فقط برای شاخه آزمایشی است؛ مخزن اصلی اسرار ازل و کافه سرکتاب خارج از محدوده تغییرند.
- وضعیت: بررسی ایستا؛ هنوز refactor یا تغییر runtime انجام نشده است.

## ۱. ترتیب بارگذاری فعلی

در `index.html` ترتیب فعلی چنین است:

1. `supabase-config.js` — تنظیم URL و publishable key
2. کتابخانه CDN یعنی `@supabase/supabase-js@2`
3. `logo.js` و یک inline script برای قرار دادن لوگو
4. `app.js?v=11` — هسته UI، داده اولیه، ناوبری، مودال‌ها، مدیریت محتوای عمومی و بخشی از ورود مدیر
5. `asrar-commerce.js?v=1` — فروشگاه، سفارش، اشتراک، پیام‌رسانی و داشبورد تجاری/مدیریتی
6. `logo-apply.js?v=1` — اعمال لوگو

CSSها: `app.css` سپس `layout-fix.css`.

## ۲. نقشه فایل‌ها و مالکیت مشاهده‌شده

| فایل/بخش | مسئولیت فعلی | وضعیت معماری |
|---|---|---|
| `index.html` | پوسته صفحه، DOM اصلی، ترتیب اسکریپت‌ها | نگه‌دارنده ساختار؛ باید از منطق تجاری خالی بماند |
| `app.js` | داده پیش‌فرض، خانه، بنر/کارت، ناوبری، مودال‌ها و محاسبات، محتوای عمومی، پنل مدیریت محتوا، Supabase و SW | بیش از حد چندمسئولیتی؛ فایل bootstrap نیست |
| `asrar-commerce.js` | فروشگاه، سفارش، رسید، اشتراک، گفتگو، داشبورد و عملیات مدیر | ماژول مستقل اما client و احراز هویت جدا دارد |
| `supabase-config.js` | تنظیمات عمومی پروژه | مناسب؛ فقط کلید عمومی |
| `app.css` | ظاهر اصلی | مالک سبک اصلی |
| `layout-fix.css` | اصلاحات تکمیلی چیدمان | باید در بازبینی CSS بررسی شود تا override دائمی نسازد |
| `logo.js` و `logo-apply.js` | داده/اعمال لوگو | دو نقطه مرتبط؛ احتمال هم‌پوشانی باید پیش از حذف بررسی شود |
| `sw.js` | Service Worker | با تصمیم online-only باید صرفاً از نظر cache آفلاین و داده حساس بازبینی شود؛ فعلاً حذف نشود |
| `manifest.webmanifest`، `favicon.svg`، `og.jpg` و `icons/` | هویت PWA و فراداده | دارایی‌های ایستا؛ از مدیریت محتوای runtime فعلی جدا هستند |

## ۳. وابستگی‌های بحرانی فعلی

### Supabase و نشست
- `app.js` در ابتدای اجرا یک client در متغیر محلی `sbClient` می‌سازد.
- `asrar-commerce.js` یک client دوم با همان URL و کلید می‌سازد.
- در نتیجه دو نمونه می‌توانند نشست، listenerها و refresh token را مستقل مدیریت کنند؛ این خلاف هدف «یک client و یک مالک نشست» است.
- هیچ سرویس مرکزی مشترک برای احراز هویت، کاربر جاری و نقش مدیر در این دو فایل دیده نمی‌شود.

### احراز هویت و مدیریت
- در `app.js` ورود مدیر از prompt ایمیل/رمز و `signInWithPassword` انجام می‌شود؛ سپس `app_metadata.role === 'admin'` بررسی می‌شود.
- در `asrar-commerce.js` نیز `requireAdmin()` prompt ایمیل/رمز و مسیر جداگانه `signInWithPassword` دارد.
- دو مسیر مستقل مدیریت و دو سطح UI مدیریت وجود دارد: پنل `#adm/#ap` در HTML و لایه مدیریت تجاری که در runtime ساخته می‌شود.
- فروشگاه/اشتراک/پیام کاربر در ماژول تجاری به `db.auth.getUser()` متکی است، اما مسیر ورود/ثبت‌نام شماره و PIN در رابط اسرار ازل هنوز پیاده نشده است.
- صفحه `prof` فقط متن placeholder است و مالک واقعی پروفایل/تنظیمات حساب ندارد.

### کافه سرکتاب به‌عنوان مرجع رفتاری
- در HTML فعلی کافه، فرم ثبت‌نام/ورود شماره تلفن و PIN هشت تا دوازده رقمی و کنترل تغییر حالت ورود وجود دارد.
- همان HTML مسیر OTP تلگرام مدیر را از مسیر ورود کاربر جدا معرفی می‌کند و modal ورود مدیر شش‌رقمی دارد.
- فایل `main.js` در دریافت فعلی GitHub محتوای قابل‌خواندن برنگرداند؛ بنابراین جزئیات پیاده‌سازی backend/Edge Function کافه هنوز تأیید نشده است.
- یادداشت امنیتی کافه نام `admin-telegram-otp` را ذکر می‌کند، اما این یادداشت به‌تنهایی اثبات نمی‌کند تابع فعلی deploy و عملیاتی است.
- پس در این مرحله فقط جداسازی رفتاری دو مسیر قابل استناد است؛ منطق داخلی کافه نباید حدس زده یا کپی شود.

## ۴. معماری مقصد (بدون وصله‌زنی)

هر قابلیت فقط یک مالک دارد:

- `services/supabase-client.js`: تنها سازنده client و مرجع واحد Supabase.
- `auth/auth-service.js`: ثبت‌نام/ورود کاربر با شماره و PIN، خروج، session و role checks؛ بدون UI.
- `auth/admin-otp-service.js`: ارتباط با مسیر OTP مدیر؛ فقط پس از تأیید سورس و قرارداد واقعی تابع سرور.
- `account/account-page.js`: پروفایل، تنظیمات حساب، تاریخ ثبت‌نام، آخرین ورود و سوابق شخصی.
- `support/support-service.js` و `support/support-ui.js`: گفتگوی دوطرفه و صندوق پیام.
- `commerce/`: کاتالوگ، سفارش، پرداخت، تخفیف و اشتراک؛ مصرف‌کننده auth-service و Supabase مشترک.
- `admin/`: یک shell مدیریتی واحد با بخش‌های محتوا، تجارت، پیام‌ها و کنترل‌های فنی؛ promptهای تکراری و دو ورودی مدیریتی حذف می‌شوند.
- `content/`: محتوای عمومی، بنرها، مودال‌ها و تنظیمات بصری.
- `ui/`: ناوبری و اجزای نمایشی مشترک.
- `app.js`: در مقصد فقط راه‌اندازی و اتصال ماژول‌ها.

این نام‌ها طرح مقصدند، نه مجوز ساخت فایل‌های خالی یا انتقال کورکورانه. ساختار کلاسیک اسکریپت‌های فعلی باید حفظ شود تا زمانی که قرارداد بارگذاری و تست مهاجرت مشخص شود.

## ۵. قراردادهای اتصال

1. فقط `services/supabase-client.js` مجاز به فراخوانی `supabase.createClient` است.
2. auth-service تنها مرجع `getUser/getSession/signOut` و بررسی نقش است.
3. commerce و account نباید مستقیماً ورود مدیر یا ساخت client انجام دهند.
4. مدیر با نقش معتبر در `app_metadata` و تأیید سمت سرور مجاز است؛ پنهان‌کردن دکمه جایگزین RLS نیست.
5. کاربر و مدیر دو مسیر احراز هویت جدا دارند؛ session و UI آن‌ها نباید با promptهای پراکنده مدیریت شود.
6. اطلاعات PIN و OTP خام در log، localStorage یا محتوای قابل‌خواندن ذخیره نشود.
7. تغییرات schema فقط با migration جدید؛ migration اعمال‌شده بازنویسی نشود.

## ۶. ترتیب اجرای سرنخ اول: حساب و ورود

1. تأیید کامل سورس Edge Function موجود اسرار ازل، قرارداد ورودی/خروجی و secrets موردنیاز؛ بررسی deploy state.
2. تأیید schema و RPCهای auth با migrationهای اعمال‌شده؛ بررسی hash، rate limit و RLS.
3. طراحی UI ثبت‌نام/ورود داخل قاب بومی اسرار ازل، بدون تغییر طرح صفحه اصلی.
4. ایجاد client واحد و auth-service؛ حذف client دوم فقط در همان تغییر یکپارچه و پس از تست.
5. ساخت پروفایل واقعی و اتصال نام/شماره/شناسه/تاریخ ثبت‌نام/آخرین ورود.
6. یکپارچه‌سازی عملیات user در commerce با auth-service.
7. مسیر OTP مدیر فقط پس از تأیید قرارداد backend؛ حذف هر دو prompt ایمیل/رمز تکراری.
8. تست ثبت‌نام، ورود، خطای PIN، rate limit، نشست، refresh، خروج، پروفایل و جداسازی نقش مدیر.
9. ثبت شواهد در completion tracker؛ سپس درخواست تأیید برای رفتن به سرنخ بعد.
