# اصول معماری و جلوگیری از تکرار خطاهای کافه سرکتاب

این سند برای مخزن آزمایشی اسرار ازل الزام‌آور است. هدف، استفاده از منطق و تجربهٔ درست کافه است، نه انتقال وصله‌ها و پیچیدگی‌های انباشته‌شدهٔ آن.

## ۱) مرجع واحد برای هر قابلیت
- برای هر قابلیت فقط یک مالک (module/service) و یک مسیر اجرای اصلی وجود داشته باشد.
- احراز هویت، session، مجوز مدیر، تنظیمات، پیام‌رسانی، سفارش و پرداخت نباید چند پیاده‌سازی موازی داشته باشند.
- هر ماژول از API عمومی و مستند ماژول مالک استفاده کند؛ دستکاری مستقیم state داخلی ماژول دیگر ممنوع است.
- قبل از افزودن قابلیت، کد موجود جست‌وجو شود؛ اگر قابلیت موجود است همان توسعه یابد، نه اینکه نسخهٔ دوم ساخته شود.

## ۲) مرزبندی فایل‌ها
- `app.js`: فقط bootstrap، ثبت ماژول‌ها، راه‌اندازی و اتصال سطح‌بالا؛ نه محل انباشتن منطق همهٔ قابلیت‌ها.
- `auth/`: ثبت‌نام، ورود، خروج، session و مجوزها.
- `account/`: پروفایل، تنظیمات حساب و سوابق شخصی.
- `support/`: گفتگو، پیام‌ها و صندوق ورودی.
- `commerce/`: کاتالوگ، سبد/سفارش، پرداخت، تخفیف و اشتراک.
- `admin/`: داشبورد و عملیات مدیریتی؛ UI و سرویس‌ها از هم جدا.
- `services/`: client واحد Supabase، دسترسی داده و سرویس‌های مشترک.
- `ui/`: اجزای عمومی رابط کاربری و ابزارهای نمایش.
- `styles/`: CSS موضوعی و محدود؛ از selectorهای سراسری و overrideهای زنجیره‌ای پرهیز شود.
این دسته‌بندی جهت معماری است؛ قبل از جابه‌جایی فایل‌های فعلی باید وابستگی‌ها و مسیر بارگذاری بررسی شوند.

## ۳) ممنوعیت وصله‌زنی
- فایل تزریقی/patch برای اصلاح دائمی رفتار برنامه اضافه نشود.
- چند listener برای یک رویداد، monkey-patch، overrideهای تکراری تابع و CSSهای متناقض ممنوع است.
- تغییر باید در ماژول مالک قابلیت و در نقطهٔ اصلی منطق انجام شود.
- migrationهای دیتابیس افزایشی و نسخه‌دار باشند؛ migration قبلیِ اعمال‌شده بازنویسی نشود.

## ۴) کنترل رشد و پیچیدگی
- هیچ فایل مرکزی نباید به محل تجمع منطق نامرتبط تبدیل شود.
- پیش از افزودن کد، مسئولیت ماژول و اثر وابستگی آن ثبت شود.
- فایل بزرگ به بخش‌های مستقل با مرز روشن تقسیم شود؛ اما خردکردن بی‌دلیل به فایل‌های تک‌تابعی نیز انجام نشود.
- سقف بازبینی پیشنهادی: فایل بیش از ۵۰۰ خط یا ماژول با چند مسئولیت مستقل باید پیش از توسعهٔ بعدی بازبینی و در صورت نیاز تفکیک شود. این سقف قانون ماشینی نیست؛ معیار بازبینی معماری است.
- هر قابلیت باید API، ورودی/خروجی، خطاها و مالک state مشخص داشته باشد.

## ۵) امنیت و داده
- دادهٔ واقعی کاربران، حساب‌ها، PINها، پیام‌ها، سفارش‌ها و سوابق کافه منتقل نشود.
- فقط ساختار، منطق تجاری و الگوهای فنی پس از بازبینی و تطبیق منتقل یا بازسازی شوند.
- Supabase client در مرورگر واحد باشد؛ secret/service_role در فرانت‌اند ممنوع.
- RLS و مجوزهای سمت سرور مرجع نهایی دسترسی هستند؛ پنهان‌کردن دکمه در UI امنیت محسوب نمی‌شود.

## ۶) آنلاین‌بودن
- برنامه آنلاین‌محور است؛ مسیر آفلاین، cache آفلاین و fallback آفلاین اضافه نشود.
- Service Worker در صورت نیاز فقط چرخهٔ نصب‌پذیری/عبور شبکه را حفظ کند و نباید منطق تجاری یا دادهٔ حساس را cache کند.

## ۷) روند بستن هر سرنخ
1. بررسی وضعیت فعلی و مالک قابلیت.
2. ثبت طرح تغییر و فایل‌ها/جداول/توابع تحت تأثیر.
3. پیاده‌سازی در محل اصلی، بدون patch.
4. تست واحد/ساختاری و تست اتصال UI → service → database/edge function.
5. بررسی امنیت، RLS، خطاها و حالت‌های مرزی.
6. ثبت نتیجه و باقی‌مانده‌ها در tracker.
7. فقط پس از تأیید کاربر، سرنخ بعدی آغاز شود.

## ۸) معیار پذیرش
- یک مسیر اصلی برای هر کارکرد.
- نبود کد تکراری یا override متناقض.
- نبود رشد بی‌رویهٔ فایل bootstrap.
- خطایابی روشن و قابل پیگیری.
- تست عملی روی شاخهٔ آزمایشی.
- مخزن اصلی اسرار ازل و کافه سرکتاب بدون تغییر باقی بمانند.
